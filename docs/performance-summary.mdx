This document provides training performance measurements for language, vision-language, and image-generation models using NeMo AutoModel with the PyTorch backend. Model names link to YAML recipes pinned to reviewed repository snapshots. The tables record the settings used for each measurement; linked recipes are starting points.

<Note>
Measurements come from different development commits, workloads, kernels, and timing windows. They are not a benchmark campaign for a single release. **Measurement Source** identifies the run supplying the numbers. **Related NeMo-CI** links to separate recipe validation or benchmark attempts; a completed job does not verify the exact numbers in the row. Short smoke tests and failed jobs are labeled. W&B and internal NeMo-CI links may require access.
</Note>

## Measurement Methods and Recipe Differences

For language and vision-language rows with a W&B source, except Qwen3.8-Flash-Next, step time is reconstructed from each logged pair of `num_tokens_per_step` and `tps`. Mean step time is the arithmetic mean of those reconstructed times. Tokens/sec/GPU is total logged tokens divided by total reconstructed time and physical GPU count. This includes any overhead in the source timer.

These W&B aggregates use training steps 10-99 inclusive, with three exceptions:

- MiMo-V2.5-Pro uses steps 10-19 from a short 20-update run with validation every five steps. Its reconstructed time can include validation overhead.
- Nemotron-3.5-Lightning uses steps 10-299.
- Kimi-Linear uses steps 10-49.

Recipe and CI differences that affect reproduction include:

- GLM-5.3 was measured with prepacked Tulu-3 data and MoE `reshard_after_forward: false`; the linked recipe and CI use online packing and `true`.
- MiMo-V2.5-Pro's related CI run changes validation frequency and logs 21 updates.
- MiMo-V2.6-Flash-RL was measured with CP1 and LBS1; the linked recipe uses CP2 and LBS2.
- Nemotron-3.5-Lightning was measured with CP1 and 8,192-token sequences; the linked Tulu-3 recipe uses CP8 and 65,536-token sequences. Its related CI link is a separate HellaSwag LoRA run.
- Kimi-Linear was measured with 4,096-token packing; the linked recipe and CI use unpacked sequences.
- Laguna-XS-2.1's source used zero dataloader workers; its related CI run uses four.
- Several CI jobs override the recipe's step limit. The Qwen3.8-27B and GLM-5.3-Flash links contain only 10 and five initial training steps, respectively.

The related CI links were checked on October 13, 2026. They cover different source commits and do not certify a single release snapshot. Failed MiMo-V2.6 Tulu-3 attempts require a newer cuDNN version; the Nemotron Super VL attempt could not retrieve the released checkpoint. The image-generation attempts produced no throughput measurement.

Image-generation rates are calculated as `GBS / step_time / physical_GPU_count`. Language and image-generation rates use different units.

`NR` means not recorded or not verified; `-` means not applicable. For the historical onboarding rows, FSDP2 is the recorded strategy but its shard degree was not verified, so the numeric FSDP column is `NR`. GA is derived as `GBS / (LBS * DP)`, where `DP = #GPUs / (TP * PP * CP)`; EP overlaps these mesh axes and is not an additional divisor. MBS is the recorded pipeline micro-batch size for PP runs and equals LBS otherwise. Unverified model FLOP estimates are `NR`.

The original mock-data benchmark rows have no recorded measurement-source link. Their related CI links identify later runs of the recipes. Those original measurements disable gradient clipping and calculate MFU using an H100 BF16 peak of 989 TFLOPs/sec; these assumptions do not apply to the W&B rows.

## Glossary

- **MFU**: Model FLOPs Utilization - ratio of achieved compute to peak hardware capability
- **TP**: Tensor Parallelism - splits individual layers across GPUs
- **PP**: Pipeline Parallelism - splits model layers into stages
- **CP**: Context Parallelism - splits the sequence across GPUs
- **FSDP**: Fully Sharded Data Parallelism - the table column gives the shard degree when verified
- **EP**: Expert Parallelism - distributes MoE experts across GPUs
- **DP**: Data Parallelism - replicates model and splits data
- **VP**: Virtual Pipeline - number of pipeline stages per GPU for interleaving
- **MBS**: Micro-Batch Size - size of one forward pass in pipeline
- **LBS**: Local Batch Size - size of one step per GPU
- **GBS**: Global Batch Size - total batch size across all GPUs
- **GA**: Gradient Accumulation - number of local-batches before optimizer step
- **TE**: Transformer Engine kernel optimizations - RMSNorm, Linear and DotProductAttention
- **DeepEP**: Deep Expert Parallelism - advanced EP routing for MoE models
- **FlexAttn**: PyTorch's [Flex Attention](https://docs.pytorch.org/docs/stable/nn.attention.flex_attention.html)
