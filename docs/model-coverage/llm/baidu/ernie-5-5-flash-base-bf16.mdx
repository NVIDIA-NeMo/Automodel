NeMo AutoModel supports full-parameter fine-tuning of
[ERNIE-5.5-Flash-Base-BF16](https://huggingface.co/baidu/ERNIE-5.5-Flash-Base-BF16),
the BF16 release of Baidu's ERNIE 5.5 Flash base checkpoint, a
Mixture-of-Experts (MoE) language model with 43 decoder layers. Layer 0
combines Heavily Compressed Attention (HCA) with a dense feed-forward network
(FFN), 36 layers combine HCA with a latent MoE, and layers 7, 14, 21, 28, 35,
and 42 combine sparse attention (DSA) with a latent MoE. Each MoE layer has 512
routed experts, 10 of which are selected per token, and one shared expert.
Manifold-constrained Hyper-Connections (mHC) carry four residual streams
through the decoder. A hyper head contracts the streams before the final norm
and the output projection, and MultiMax corrects the logits. The checkpoint
also stores one multi-token prediction (MTP) block.

<Note>
This page covers two configurations of the 43-layer main decoder with expert
parallelism (EP) and FSDP2 on single unpacked documents: full-parameter
supervised fine-tuning (SFT) on 16 nodes and [LoRA](#lora) on 2 nodes.
[Current Scope](#current-scope) lists what is outside them.

</Note>

## Fine-Tune ERNIE-5.5-Flash-Base-BF16

The full fine-tuning recipe runs full-parameter SFT of the 43-layer main
decoder on 64 GPUs (16 nodes with 4 GB200 GPUs per node), so it is not a
single-node example. It loads the model and the tokenizer from revision
`68d19ee51c032344fa0a8018e7dc21b2668a55c4` of
`baidu/ERNIE-5.5-Flash-Base-BF16` on the Hugging Face Hub, both with
`trust_remote_code: false`, and the train and validation splits of
`rajpurkar/squad`. Every node must be able to read them, and the weights take
about 534 GiB in the Hub cache. The 64-GPU training runs with HybridEP under
[Validated Configuration](#validated-configuration) read them from caches on a
file system shared by the nodes, with `HF_HUB_OFFLINE=1`,
`TRANSFORMERS_OFFLINE=1`, and `HF_DATASETS_OFFLINE=1`. A download through the
recipe was not run. Run the recipe from the repository root on each of the 16
nodes, with `NODE_RANK` set from 0 to 15 and `MASTER_ADDR` set to the first
node:

```bash
uv run torchrun --nnodes=16 --nproc-per-node=4 --node-rank=$NODE_RANK --master-addr=$MASTER_ADDR --master-port=29500 \
  -m nemo_automodel.cli.app examples/llm_finetune/ernie5_5/ernie5_5_flash_squad_ep.yaml
```

The 100-update validation run did not start this module. It started the
recipe through a script that gives every rank its own compile-cache
directories (`TRITON_CACHE_DIR`, `TORCHINDUCTOR_CACHE_DIR`, `CUDA_CACHE_PATH`,
and `TORCH_EXTENSIONS_DIR`) and then makes the calls this module makes in a
worker process: it parses the configuration, constructs the recipe, and runs
its setup and its training loop. The script also times every update and
records the peak allocated memory. The step times and the allocated memory
in the table under [Validated Configuration](#validated-configuration) are
its measurements. Set these directories per rank if the ranks of a node would
otherwise share a cache directory on a network file system. The routed
experts exchange tokens through HybridEP,
which compiles its kernels at the first dispatch of every process and writes
them to a directory named after the process id under `HYBRID_EP_CACHE_DIR`, or
under the home directory when that variable is unset. The validation runs set
`HYBRID_EP_CACHE_DIR` to a separate directory of the job on every node. Do the
same if the nodes share the home directory. HybridEP compiles with `nvcc` from
`CUDA_HOME`, which must be present at run time. The repository's shared kernel
cache (`NEMO_HYBRIDEP_JIT_CACHE`) was not used in the validation runs. They left
`NUM_OF_HYBRID_EP_RANKS_PER_NVLINK_DOMAIN` unset, so that HybridEP detects
which ranks of an expert group share an NVLink domain. An expert group is 8
consecutive ranks (`ep_size: 8`), that is, the two nodes with `NODE_RANK` values `2k`
and `2k+1`. These two nodes must be in one NVLink domain: on GB200 a domain can
span several four-GPU nodes, and an expert group that is split over two
domains has not been validated. Without `uv run` and without that script, the
command was run on 64 GPUs for 10 updates, with
`--step_scheduler.max_steps=10` and a `--checkpoint.checkpoint_dir` appended
and without `checkpoint.load_metadata_with_gloo`. Its first update took 90 s.
With `--nnodes=1`, a three-layer model as
`--model.pretrained_model_name_or_path`, `--distributed.ep_size=2`,
`--step_scheduler.global_batch_size=4`, and the same two overrides, the
recipe as it ships was run on one node for 10 updates.

Dense parameters use FSDP2, and the routed experts of each MoE layer are
distributed over the EP group. The parameters of the DSA indexers are frozen.
The router correction bias is a fixed buffer, not a parameter. The MTP block is
not loaded or trained.

| Recipe | Dataset | Description |
|---|---|---|
| [ernie5_5_flash_squad_ep.yaml](https://github.com/NVIDIA-NeMo/Automodel/blob/main/examples/llm_finetune/ernie5_5/ernie5_5_flash_squad_ep.yaml) | SQuAD | Full-parameter SFT of the 43-layer decoder with EP and FSDP2; checkpoint saving disabled because of the checkpoint size |
| [ernie5_5_flash_squad_ep_lora.yaml](https://github.com/NVIDIA-NeMo/Automodel/blob/main/examples/llm_finetune/ernie5_5/ernie5_5_flash_squad_ep_lora.yaml) | SQuAD | LoRA on the 43-layer decoder with EP and FSDP2 on 2 nodes; adapter checkpoints enabled; see [LoRA](#lora) |

The six DSA layers run through the cuDNN sparse-attention path
(`model.backend.attn: cudnn`). This path requires
`nvidia-cudnn-frontend[cutedsl]` and FlashMLA. It is validated on SM100-class
GPUs (GB200) only. The values `eager`, `torch`, and `sdpa` select an eager DSA
path that accepts at most 512 tokens per document.

A DSA layer attends to a local window of 128 keys and to the 2,048 remote keys
with the highest index scores, so it discards keys only from position 2,176 of
a document on. Training of the released model was validated with documents
of at most 256 tokens, where every key is selected. The key selection was
exercised in a forward pass over documents of 4,096 tokens (refer to
[Numerical Validation](#numerical-validation)) and in one training run of a
three-layer model (refer to [Validated Configuration](#validated-configuration)).

Multi-GPU training of the released model has been validated with the cuDNN
path only. `model.backend.linear` must be `torch`. `experts` and `dispatcher`
must be `torch_mm` and `hybridep`, the pair of the recipe, or `torch` and
`torch`. The first pair exchanges the routed tokens through HybridEP and
requires BF16 compute: `model.dtype: bfloat16` and an FSDP `param_dtype` of
`null` or `bfloat16`. The second pair exchanges the tokens with all-gather and
all-reduce over the EP group. The checkpoint and parity results on this page
that name it were measured with it. All remaining fields except
`enable_hf_state_dict_adapter` must keep their defaults, the tuning fields of
HybridEP among them. The model rejects every other `model.backend` setting.

Parameters use BF16, the dtype of the released checkpoint, except where the
model keeps FP32 parameters, among them the mHC, hyper-head, router, and
latent-projection parameters. The four mHC residual streams stay in FP32
between decoder blocks: each block
computes the mHC coefficients, collapses the streams into the layer input, and
expands the layer output back into the streams in FP32 with autocast disabled.
The hyper head contracts the streams in FP32.

<Note>
The full fine-tuning recipe sets `checkpoint.enabled: false` because one checkpoint of the full
model and optimizer is about 3.1 TiB: 523 GiB of weights and 2.5 TiB of
optimizer state. To save, set `checkpoint.enabled: true` and
`checkpoint.save_consolidated: false`. The validated save of the full model,
run with the `torch` expert and dispatcher backends, wrote one checkpoint, with
`step_scheduler.ckpt_every_steps: 100` and `dist_env.timeout_minutes: 180`. The
full fine-tuning recipe's values of 50 and 30 were not run with saving enabled.
[Validated Configuration](#validated-configuration) lists what was saved and
restored. The consolidated Hugging Face export has not been validated.

</Note>

The checkpoint adapter supports the two expert layouts that the shared MoE
parallelizer produces: experts sharded over several data-parallel ranks per
expert group, and one rank per expert group (for example, 2 GPUs with
`ep_size: 2`). Both layouts were saved and restored on GPUs with a three-layer
model built from released layers with the `torch` backends. With HybridEP, the
layout with experts sharded over several ranks per expert group was saved and
restored ([Validated Configuration](#validated-configuration)).

A checkpoint load reads into the storage of the model and is not
transactional. A load that fails can leave the model partly overwritten, and
the adapter then rejects every later load and save. Discard the model and its
adapter after a failed load, and do not continue training with them.

See the [Slurm Launcher Guide](/job-launchers/slurm-cluster) and
[Installation Guide](/get-started/installation) for setup.

## LoRA

The LoRA recipe trains rank-8 adapters on the 43-layer main decoder on 8 GPUs
(2 nodes with 4 GB200 GPUs per node). The released weights are loaded and stay
frozen. Run it from the repository root on each of the 2 nodes, with
`NODE_RANK` set to 0 and 1 and `MASTER_ADDR` set to the first node:

Both nodes of the 8-rank expert group must be in one NVLink domain. HybridEP
requires DeepEP with HybridEP support and compiles kernels on first use. Leave
`NUM_OF_HYBRID_EP_RANKS_PER_NVLINK_DOMAIN` unset; if the nodes share a home
directory, set `HYBRID_EP_CACHE_DIR` to a separate directory on each node.

```bash
uv run torchrun --nnodes=2 --nproc-per-node=4 --node-rank=$NODE_RANK --master-addr=$MASTER_ADDR --master-port=29500 \
  -m nemo_automodel.cli.app examples/llm_finetune/ernie5_5/ernie5_5_flash_squad_ep_lora.yaml
```

The recipe keeps the model, the data, the precision policy, and the optimizer
of the full fine-tuning recipe. It adds the `peft` section, runs one document
per rank on 8 ranks (global batch size 8), sets the learning rate to 1.0e-5,
and enables adapter checkpoints. With `ep_size: 8` on 8 ranks, every rank owns
one of the 8 expert groups of each MoE layer.

LoRA removes the gradients and the optimizer state of the base weights, which
is what lets 2 nodes take the place of 16. It does not reduce the weights that
a GPU holds: every GPU keeps one eighth of the routed experts and its shard of
the dense weights. In the `torch` backend run these occupied 65.8 GiB after
loading. A training step still gathers the dense weights and keeps the
activations of the forward pass for the backward
pass; in the validated run the allocation rose from 65.8 GiB to a peak of
102.8 GiB.

### LoRA Targets

LoRA is supported on the plain linear projections that an attention module
owns directly (not those of its indexer or compressor), on the routed experts,
and on the projections of the dense FFN and of the shared expert. The recipe
selects all of them.

| Modules under `model.layers.*` | Layers | LoRA |
|---|---|---|
| `attention.wq_a`, `attention.wq_b`, `attention.wkv`, `attention.wo_b` | 37 HCA layers | Supported |
| `attention.gate_proj` | 43 layers | Supported |
| `attention.q_a_proj`, `attention.q_b_proj`, `attention.kv_a_proj_with_mqa`, `attention.o_proj` | 6 DSA layers | Supported |
| `moe.experts` | 42 MoE layers | Supported; 98% of the adapter parameters |
| `mlp.gate_proj`, `mlp.up_proj`, `mlp.down_proj` | Layer 0 | Supported |
| `moe.shared_experts.gate_proj`, `moe.shared_experts.up_proj`, `moe.shared_experts.down_proj` | 42 MoE layers | Supported |
| `attention.wo_a` | 37 HCA layers | Rejected: a grouped projection with its own forward |
| `moe.fc1_latent_proj`, `moe.fc2_latent_proj` | 42 MoE layers | Rejected: FP32 projections with their own forward |
| `attention.indexer.wq_b`, `attention.indexer.wk`, `attention.indexer.weights_proj` | 6 DSA layers | Rejected: the indexers are frozen |
| `attention.compressor.wkv`, `attention.compressor.wgate` | 37 HCA layers | Rejected: not validated |
| `attention.k_b_proj`, `attention.v_b_proj`, `moe.gate`, the mHC parameters, the norms | | Cannot be selected: parameters without a linear module of their own |

The output head `model.lm_head` is rejected as not validated. An adapter on a
rejected module is an error when the model is parallelized, before it is
sharded and before any weight is read. Without `peft.target_modules`, the
default pattern of the LoRA configuration, `*_proj`, selects rejected
projections, so list the targets as the recipe does. DoRA (`peft.use_dora`) is
rejected on every target when the model is built. An adapter in another dtype
than the weight it adapts is rejected when the model is parallelized. There
are two ways to get one: `peft.lora_dtype` set to another dtype, and a model
loaded in FP32 under a BF16 FSDP compute dtype
(`distributed.mp_policy.param_dtype`, BF16 when no policy is given), because
the frozen weights of a LoRA run are then stored in BF16 while the adapters
stay FP32. The recipe loads the model in BF16 and sets the compute dtype to
`null`.

### LoRA Checkpoints

A LoRA checkpoint holds the adapter and the state needed to resume, not the
base weights:

| Content | Size |
|---|---|
| `model/adapter_model.safetensors`: 856 BF16 adapter tensors | 3.34 GiB |
| `optim/`: optimizer state of the adapter, one file per rank | 16.71 GiB |
| `model/adapter_config.json`, `model/automodel_peft_config.json`, tokenizer files, `config.yaml`, `losses.json`, and data-loader, random-number, and scheduler state | 15 MiB |
| Total | 20.06 GiB |

The recipe writes one checkpoint after 50 updates and one after 100, 40 GiB
in all. In the `torch` backend run, the two saves took 10.1 and 8.5 s.

A resume loads the released checkpoint first and then the adapter; it was
validated with the same number of ranks and the same `ep_size`. It restores
the adapter exactly. The state of the recipe's optimizer (Transformer Engine
`FusedAdam`: moments, master weights, and the update counter) is restored only
with the fix of pull request
[#4739](https://github.com/NVIDIA-NeMo/Automodel/pull/4739). A version without
that fix restarts the optimizer silently on the restored adapter: no error is
raised, the moments start empty, and the update counter starts again.

A run resumes from the checkpoint directory that `checkpoint.restore_from`
names; the two runs below were started that way. Without
`checkpoint.restore_from`, a run looks for the latest checkpoint in
`checkpoint.checkpoint_dir` and resumes from it if the check of its model
configuration against the run's accepts it; a checkpoint that this check
reports as incompatible is skipped. A second run of the recipe in the same
directory is therefore normally a resume. That second way was not run with
LoRA for this model.

Both cases used the `torch` expert and dispatcher backends on the 43-layer
model from the checkpoint written after 50 updates, each in a new process that
loaded the released checkpoint (142 and
129 s), restored the adapter (5 and 9 s), and trained 8 more updates
(`step_scheduler.max_steps: 58`, no save):

| Library | Adapter | Optimizer state | Update counter |
|---|---|---|---|
| With the change of #4739 | All 856 tensors hold the saved bytes on every rank | All 2,568 tensors hold the saved bytes on every rank | 50, as saved |

Both processes exited without an error. Training is not bit-reproducible from
run to run, so a resumed run does not repeat the uninterrupted run bit for

seven updates the loss differed from the uninterrupted run by at most 0.0070
with the restored optimizer state and by at most 0.0164 without it; in three
of the seven updates the run without it was the closer one. The validation
loss after the eight updates was 0.1317 with the restored optimizer state and
0.1316 without it, on 367 label tokens. One run of eight updates in each case
does not separate the two cases by their loss.

### Adapter Format

`model/adapter_model.safetensors` stores the adapter tensors under the
parameter names of NeMo AutoModel with the prefix `base_model.model.`:
`lora_A.weight` and `lora_B.weight` for every adapted linear projection, and
`lora_gate_and_up_A`, `lora_gate_and_up_B`, `lora_down_A`, and `lora_down_B`
for the routed experts of every MoE layer, each with the 512 experts on its
first axis. `adapter_config.json` lists the 344 adapted linear projections. It
does not list the 42 expert modules, although their tensors are in the file;
`automodel_peft_config.json` keeps the target patterns of the recipe. A resume
installs the adapters from the `peft` section of the run and reads their
tensors from `adapter_model.safetensors`; it does not use the list in
`adapter_config.json`. A LoRA run writes no consolidated Hugging Face export,
whatever `checkpoint.save_consolidated` says. Loading the adapter with Hugging
Face PEFT and merging it into the base weights with
`export_merged_peft_checkpoint` have not been tested.

## Loading and Inputs

Both recipes load revision `68d19ee51c032344fa0a8018e7dc21b2668a55c4` of
`baidu/ERNIE-5.5-Flash-Base-BF16`. The released configuration declares the
`Ernie5_5_MoeForCausalLM` architecture and `model_type: ernie5_5_moe`, which
NeMo AutoModel resolves through its own registry.

The released configuration sets `num_nextn_predict_layers: 1`, and the
checkpoint stores the MTP block as 1,582 keys under `model.layers.43.*`. This
implementation does not construct that block: a non-zero
`num_nextn_predict_layers` is rejected when the model is constructed, so the
released configuration cannot be loaded unchanged. Set
`model.num_nextn_predict_layers: 0` to load the 43 decoder layers. The MTP keys
of the checkpoint are then not loaded. Both example recipes set it. A
configuration that does not come from the released file defaults to 0.

Inputs are single unpacked documents. The model's `forward` accepts one
unpadded document, `input_ids` of shape `[1, sequence]`, which the recipes
provide with `step_scheduler.local_batch_size: 1`. `forward` rejects a padded
batch, and THD sequence packing is refused when the data loader is built.
`forward` returns the logits only, without a loss or a cache. It rejects
`input_ids` that contain the configured `pad_token_id`, an `attention_mask` or
a `padding_mask` that marks padding, and `position_ids` other than 0 to
`sequence - 1`. It cannot detect several documents that are concatenated into
one row without such masks or positions, so the data pipeline must supply one
document per row.

## Current Scope

Supported: full-parameter SFT and LoRA of the 43-layer main decoder with EP and
FSDP2 on single unpacked documents. The following limits apply:

- The MTP block is not loaded or trained. Its 1,582 checkpoint keys under
  `model.layers.43.*` are excluded, and loading requires
  `model.num_nextn_predict_layers: 0`.
- The parameters of the DSA indexers are frozen, and a `freeze_config` unfreeze
  selector that covers a DSA indexer is an error at the first training step.
  A LoRA adapter on an indexer projection is rejected when the model is
  parallelized.
  The router correction bias is a fixed buffer, not a parameter. No indexer
  loss is computed. The reference training recipe trains the indexers with a KL
  term against the attention distribution, which this implementation does not.
- Tensor parallelism (TP), context parallelism (CP), and pipeline parallelism
  (PP) are not supported and raise an error. Packed sequences are refused
  when the data loader is built.
- `distributed.strategy` other than `fsdp2`, `dp_replicate_size` other than 1,
  `ep_size` of 1, activation checkpointing, and an FSDP compute dtype other
  than FP32 or BF16 are rejected when the model is parallelized. With the
  HybridEP dispatcher, a model dtype or an FSDP compute dtype other than BF16
  is rejected there as well.
- The number of ranks must divide the 64 attention heads of the DSA layers, so
  a job has 2, 4, 8, 16, 32, or 64 ranks. A checkpoint stores the key and
  value projections of a DSA layer as one matrix, and it is loaded and saved
  only when every rank holds the rows of whole heads. Other rank counts are
  rejected when the model is parallelized.
- A KV cache is not supported: `forward` raises an error when `use_cache` is
  true.
- LoRA is validated with the targets, adapter rank 8 (`peft.dim`), and alpha
  32 of the LoRA recipe, with one rank per expert group, and with documents of
  at most 256 tokens. The modules that [LoRA Targets](#lora-targets) lists as
  rejected raise an error when the model is parallelized. DoRA
  (`peft.use_dora`) is rejected on every target when the model is built, and
  an adapter in another dtype than the weight it adapts when the model is
  parallelized (see [LoRA Targets](#lora-targets)). `peft.dropout` is not
  applied to the adapters of the routed experts, which hold 98% of the adapter
  parameters, and dropout on the linear projections was not validated. Not
  validated: `peft.moe_rank_scaling`, the full model with more ranks than
  `ep_size`, merging an adapter into the base weights with
  `export_merged_peft_checkpoint`, and loading an adapter with Hugging Face
  PEFT. A resume restores the optimizer state only with the change of pull
  request #4739; see [LoRA Checkpoints](#lora-checkpoints).
- Documents longer than 512 tokens require the cuDNN sparse-attention path of
  the DSA layers, which requires `nvidia-cudnn-frontend[cutedsl]` and FlashMLA
  and is validated on SM100-class GPUs (GB200) only. Multi-GPU training of the
  released model has been validated with that path only, and with documents of
  at most 256 tokens. With longer documents, the forward pass of the released
  model was run with the `torch` expert and dispatcher backends only. With
  LoRA, an earlier state of the code ran three updates each at 384, 512,
  768, and 1,024 tokens to measure memory (113 to 161 GiB allocated at the
  peak); this is not a validation. From position 2,176 of a document on, two
  forward passes of the same document can give different losses. In a
  three-layer model this was traced, with the `torch` backends, to the top-k
  step, which does not choose the same key among keys with equal index scores
  every time.
- Full-parameter training is not bitwise repeatable between runs. On the cuDNN
  sparse-attention path, no two full-parameter runs that were compared gave the
  same losses after the first update. This includes runs of the released model
  on documents of at most 256 tokens, where the DSA layers select every key.
- The full fine-tuning recipe sets `checkpoint.enabled: false` because of the
  checkpoint size (about 3.1 TiB with optimizer state). Saving and resuming
  full fine-tuning were run once on the full model and on a three-layer model
  with 16 and with 2 GPUs, with the `torch` expert and dispatcher backends,
  and with HybridEP on a three-layer model with 4 and with 16 GPUs, each time
  with the same number of ranks before and after and with
  `checkpoint.save_consolidated: false`. A resume loads the released
  checkpoint before the saved one. The consolidated Hugging Face export and
  a resume on a different number of ranks have not been validated. A saved
  checkpoint of full fine-tuning contains the 43 decoder layers and declares
  no MTP block.
