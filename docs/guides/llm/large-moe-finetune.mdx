## Introduction

Mixture-of-Experts (MoE) architectures have become the dominant design for frontier language models, activating only a fraction of their total parameters per token to deliver strong performance at reduced compute cost. This guide walks through fine-tuning four example MoE LLMs with NVIDIA NeMo AutoModel. For a full list of supported architectures, see the [LLM model coverage](/model-coverage/large-language-models/overview) page.

| Model | Hugging Face Checkpoint | Validated Using |
|-------|--------------|-----------------|
| GLM-5 | [`zai-org/GLM-5`](https://huggingface.co/zai-org/GLM-5) | 256 H100 GPUs (32 nodes x 8) |
| MiniMax-M2.5 | [`MiniMaxAI/MiniMax-M2.5`](https://huggingface.co/MiniMaxAI/MiniMax-M2.5) | 64 H100 GPUs (8 nodes x 8) |
| Step-3.5 Flash | [`stepfun-ai/Step-3.5-Flash`](https://huggingface.co/stepfun-ai/Step-3.5-Flash) | 64 H100 GPUs (8 nodes x 8) |
| DeepSeek-V3.2 | [`deepseek-ai/DeepSeek-V3.2`](https://huggingface.co/deepseek-ai/DeepSeek-V3.2) | 256 H100 GPUs (32 nodes x 8) |

To set up your environment to run NeMo AutoModel, follow the [installation guide](/get-started/installation).

## Data

### HellaSwag Dataset

All four recipes use the [HellaSwag](https://huggingface.co/datasets/rowan/hellaswag) dataset, a commonsense natural language inference benchmark where the model must predict the most plausible continuation of a given scenario.

- **Source**: `rowan/hellaswag`
- **Split**: `train` (used for both training and validation in these recipes)
- **Task**: Next-token prediction on commonsense sentence completions

For details on how to swap in your own dataset, see the [LLM Dataset Guide](/datasets/text-dataset) and the [Dataset Overview](/datasets/overview).

## Configure HybridEP Routing

Several large-scale MoE recipes use the [HybridEP dispatcher](https://github.com/deepseek-ai/DeepEP/tree/hybrid-ep) to combine expert-parallel token permutation and communication. Select it in the model backend:

```yaml
model:
  backend:
    experts: torch_mm
    dispatcher: hybridep
```

HybridEP supports two routing-metadata paths:

- **Dense routing (default)**: Builds a Boolean routing map with shape `[tokens, experts]` and a matching dense probability tensor.
- **Compact routing (opt-in)**: Passes top-k expert indices with shape `[tokens, top_k]` instead of the dense Boolean routing map. NeMo AutoModel still expands the routing probabilities to `[tokens, experts]` to preserve the existing router-gradient layout.

Enable compact routing only after benchmarking the exact model, batch shape, GPU, and expert-parallel topology:

```yaml
model:
  backend:
    experts: torch_mm
    dispatcher: hybridep
    dispatcher_hybridep_compact_routing: true
```

Compact routing reduces routing-map size, but its additional metadata preprocessing can increase latency for some workloads. Dense routing therefore remains the default.

The following advanced settings apply only when `dispatcher: hybridep`:

| Setting | Default | Description |
|---|---:|---|
| `dispatcher_hybridep_compact_routing` | `false` | Pass top-k expert indices instead of a dense Boolean routing map. |
| `dispatcher_hybridep_permute_fusion` | `false` | Fuse token permutation into dispatch and unpermutation into combine. |
| `dispatcher_hybridep_num_sms_preprocessing` | `null` | Override the number of SMs used for routing-metadata preprocessing. |
| `dispatcher_hybridep_num_blocks_permute` | `null` | Override the number of dispatch permutation blocks. |
| `dispatcher_hybridep_num_blocks_unpermute` | `null` | Override the number of combine unpermutation blocks. |
| `dispatcher_capacity_factor` | `null` | Capacity mode for dynamic routing: size the dispatch buffers once from the first real batch times this factor and run later dispatches non-blocking; an overflow trips a device-side assert. Not for experts with `expert_bias`. |
| `dispatcher_equal_token_counts` | `false` | Declare that every EP rank dispatches the same row count, so the per-dispatch pad-size all-reduce and its host sync are skipped. Keep `false` for variable-length or packed inputs: with genuinely unequal (aligned) row counts the HybridEP collective hangs silently instead of raising. |

Leave the numeric tuning settings unset to use HybridEP defaults unless a matched benchmark demonstrates an improvement. A value that improves performance on one GPU architecture or topology might reduce performance on another.

## Configure NCCL-EP

NCCL-EP is an experimental, opt-in dispatcher for BF16 expert-parallel training
on Hopper or newer GPUs. Select it with an explicit upper bound on the number
of tokens entering each MoE layer on each rank per microbatch:

```yaml
model:
  backend:
    experts: torch_mm
    dispatcher: nccl_ep
    nccl_ep:
      max_tokens_per_rank: 4096
```

Use the same bound on all EP ranks and layers. Include masked tokens and account
for local batch size and sequence parallelism when choosing it. The transport
rounds the bound up to a multiple of 64 and accepts any shorter input without
padding; receive buffers are sized from the actual routing counts, so tokens are
not dropped. The initial implementation uses eager dispatch and does not support
capturing communication in CUDA Graphs or `dispatcher_async_dispatch: true`.

NCCL-EP sizes its dispatch and combine kernels itself, so `dispatcher_num_sms`
does not apply. To tune that budget, set `NCCL_EP_COMM_SMS` in the job
environment. Received tokens use NCCL-EP's ordered
expert layout, which activation-checkpoint recomputation requires and which keeps
expert gradients reproducible from run to run.

By default each dispatch sizes its receive buffer from the routing counts, which
requires one host synchronization per MoE layer. With the `torch_mm` experts
backend, `nccl_ep.recv_capacity_factor` instead gives every dispatch a fixed
receive buffer of `max_tokens_per_rank` (rounded up to a multiple of 64) times
top-k times the factor rows, and removes that synchronization:

```yaml
model:
  backend:
    experts: torch_mm
    dispatcher: nccl_ep
    nccl_ep:
      max_tokens_per_rank: 4096
      recv_capacity_factor: 1.25
```

Rows past the routed count are left unused. A rank that receives more rows than
the capacity aborts with a device-side error instead of dropping tokens, so
choose a factor that covers the routing skew of the model; balanced routing
needs about 1.0. The fixed buffers increase expert activation memory by up to
the same factor. Experts with bias terms do not support this mode.

When all ranks of the EP group share one NVLink domain, such as one H100 node or
one GB200 NVL72 rack, setting `NCCL_EP_HT_EM_PULL_PUSH=1` in the job environment
selects NCCL-EP's NVLink pull-dispatch and push-combine kernels. They can reduce
dispatch and combine time for balanced routing but can be slower when routing is
heavily skewed. NCCL-EP rejects this setting when the EP group spans several
NVLink domains.

The runtime requires an NCCL-EP-enabled Transformer Engine build with
`transformer_engine.pytorch.ep` and NCCL 2.30.4 or newer. CI builds enable
`TE_WITH_NCCL_EP=1` on the PyTorch base image and verify the packaged library and
JIT headers. Public-wheel installations retain `NVTE_WITH_NCCL_EP=0` because
their PyTorch headers do not support that build. All NCCL-EP layers in a process
must share the same EP group, token bound, hidden width, expert count, and top-k.
Communication state is initialized during expert parallelization, before
activation checkpointing, and released before process-group teardown.

Run the focused two-GPU validation in an enabled container:

```bash
CUDA_VISIBLE_DEVICES=0,1 torchrun --standalone --nproc_per_node=2 \
  tests/functional_tests/moe/run_nccl_ep_parity.py
```

## Launch Training

NeMo AutoModel supports direct Slurm submission, local interactive runs through the NeMo AutoModel CLI, and external `torchrun`. For full details on Slurm batch jobs, multi-node configuration, environment variables, and other launch options, see the [Run on a Cluster](/job-launchers/slurm-cluster) guide.

### NeMo AutoModel CLI

```bash
uv run automodel your_single_node_config.yaml --nproc-per-node 8
```

The CLI takes the recipe config as its positional argument. Use this form only
with a config whose distributed topology fits one node; the four configs above
use multi-node PP/EP sizes and should be launched through Slurm or external
`torchrun` as shown below.

### Torchrun

```bash
export TRANSFORMERS_OFFLINE=1
export HF_HOME=your/path/to/hf_cache
export HF_DATASETS_OFFLINE=1
export WANDB_API_KEY=your_wandb_key
export MASTER_ADDR=${MASTER_ADDR:?Set MASTER_ADDR to the rank-0 hostname}
export MASTER_PORT=${MASTER_PORT:-29500}

torchrun --nproc-per-node=8 \
         --nnodes=32 \
         --rdzv_backend=c10d \
         --rdzv_endpoint="${MASTER_ADDR}:${MASTER_PORT}" \
  -m nemo_automodel.recipes.llm.train_ft \
    -c examples/llm_finetune/glm/glm_5_hellaswag_pp.yaml \
    --model.pretrained_model_name_or_path=/your/local/model_weights
```

This command uses the GLM-5 config and its `model.pretrained_model_name_or_path`
field. For another recipe, replace the `-c` path and `--nnodes`, then update the
model and tokenizer path fields defined by that YAML.

### Before You Start

- Hugging Face applies rate limits on downloads. Clone the model repository to your local filesystem beforehand.
- Ensure your Hugging Face cache (`HF_HOME`) is configured and that the dataset is already cached locally.
- To enable Weights & Biases logging, set your `WANDB_API_KEY` and configure the `wandb` section in the YAML file.
