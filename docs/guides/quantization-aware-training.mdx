QAT simulates quantization during training so trainable weights can adapt to
quantization error. NeMo Automodel provides two distinct modes through
`nemo_automodel.components.quantization.qat.QATConfig`:

| Mode | Trainable weights | Quantization |
| --- | --- | --- |
| Legacy TorchAO | Full-parameter BF16 SFT, without PEFT | INT4 weights; optional dynamic INT8 activations |
| Targeted merged-weight QAT | LoRA adapters on frozen floating-point bases | FP8 or MXFP4 weights selected independently of PEFT |

Neither mode guarantees better task quality than post-training quantization
(PTQ), lower training memory, or faster inference. Measure the intended workload
and deployment backend rather than inferring improvements from the bit width.

## Legacy full-parameter TorchAO QAT

Use the installed repository environment, including TorchAO, and BF16 model
parameters. Add this section to a complete SFT recipe **without `peft`**:

```yaml
qat:
  enabled: true
  fake_quant_after_n_steps: 0
  qat_config:
    _target_: nemo_automodel.components.quantization.qat.QATConfig
    quantizer_type: int8_dynact_int4weight
    groupsize: 256
```

`int8_dynact_int4weight` fake-quantizes eligible weights to INT4 and activations
to dynamic INT8. Choose `int4_weight_only` instead to keep activations in BF16.
TorchAO prepares eligible `nn.Linear` layers, not necessarily every projection.
Input dimensions must satisfy the group-size constraints; weight-only INT4 also
has bias and kernel tile constraints. Inspect the prepared model.

The existing [Llama 3.2 INT4 recipe](https://github.com/NVIDIA-NeMo/Automodel/blob/main/examples/llm_finetune/llama3_2/llama3_2_1b_squad_qat.yaml)
retains its original settings, including a requested one-step delay. Override
that delay for new runs: nested TorchAO modules do not reliably honor positive
`fake_quant_after_n_steps` values in the current recipe.

```bash
uv run --no-sync automodel examples/llm_finetune/llama3_2/llama3_2_1b_squad_qat.yaml --nproc-per-node 8 --qat.fake_quant_after_n_steps 0
```

This example needs model/data access and eight GPUs. `--no-sync` assumes
dependencies are already installed. Legacy TorchAO conversion is separate from
the targeted reference-export API below; validate its converted model using the
matching [TorchAO quantizer and inference kernels](https://github.com/pytorch/ao/tree/main/torchao/quantization/qat).

## Targeted LoRA FP8 / MXFP4 QAT

PEFT chooses where adapters are installed. QAT chooses which of those adapters
receive fake quantization, using case-sensitive **full module-name shell globs**.
The selectors are independent: QAT can cover only a subset of PEFT targets.
For example, adapt q/v projections but quantize only q projections:

```yaml
peft:
  _target_: nemo_automodel.components._peft.lora.PeftConfig
  target_modules: ['*.q_proj', '*.v_proj']
  dim: 4
  alpha: 8
  dropout: 0.0
  use_dora: false
  use_triton: false
  use_memory_efficient_lora: false

qat:
  enabled: true
  fake_quant_after_n_steps: 0
  qat_config:
    _target_: nemo_automodel.components.quantization.qat.QATConfig
    target_modules: ['*.q_proj']
    weight:
      format: fp8
      block_size: [32, 32]
```

For grouped experts or multiple numerical settings, replace `target_modules`
and `weight` under `qat_config` with `rules`. This GLM example requires PEFT on
the same expert modules:

```yaml
qat:
  enabled: true
  fake_quant_after_n_steps: 0
  qat_config:
    _target_: nemo_automodel.components.quantization.qat.QATConfig
    rules:
      - target_modules: ['model.language_model.layers.*.mlp.experts']
        weight:
          format: fp8
          block_size: [128, 128]
          scale_format: float32
```

Nested rule/weight mappings are typed by `ConfigNode.instantiate()`; they do not
need nested `_target_` entries. Do not mix `rules` with the simple form, or mix
either targeted form with `quantizer_type` / TorchAO kwargs. Unmatched selectors,
overlapping rules, non-LoRA targets and tied LoRA base projections are rejected.
Legacy INT4 with PEFT and targeted full-parameter FP8/MXFP4 are unsupported.

### Numerical contract

The forward pass quantizes and dequantizes the effective weight
`W + (alpha / rank) * B @ A`; gradients update the adapters while the base stays
frozen. Untargeted adapters train normally and export as merged floating weights.
Training storage and activations are not packed FP8/FP4. Use matching base/adapter
storage dtypes, zero dropout, no DoRA, and no autocast for the targeted examples.

| Weight format | Supported block sizes | Scale format |
| --- | --- | --- |
| FP8 E4M3FN | `[32, 32]` or `[128, 128]` (default) | `e8m0` (default) or explicit `float32` |
| MXFP4 E2M1 | `[1, 32]` (default) | `e8m0` only |

Blocks apply to `[out, in]` dense or canonical `[experts, out, in]` grouped
weights, including gate/up and down projections; dimensions must be divisible
by the block sizes. E8M0 uses power-of-two scales. FP32 scales use
`max(block_amax, 1e-12) / 448` without power-of-two rounding.

**GLM-5.3-Flash uses FP8 block128 with explicit `scale_format: float32`.**
This matches its decoded scale layout, not a proven bit-exact reproduction of
the original checkpoint encoder. **DeepSeek-V4 uses MXFP4 group32 with E8M0**,
which is also the default when `scale_format` is omitted. Older reference
manifests without this field decode as E8M0.

## Examples and supported training

| Example | Scope |
| --- | --- |
| [Qwen3-0.6B](https://github.com/NVIDIA-NeMo/Automodel/blob/main/examples/llm_finetune/qwen/qwen3_0p6b_lora_qat.yaml) | Two-step SQuAD, q/v LoRA FP8; configured for one GPU |
| [DeepSeek-V4-Flash](https://github.com/NVIDIA-NeMo/Automodel/blob/main/examples/llm_finetune/deepseek_v4/deepseek_v4_flash_hellaswag_experts_qat.yaml) | Experimental full pretrained backbone, expert MXFP4, EP32 |
| [GLM-5.3-Flash](https://github.com/NVIDIA-NeMo/Automodel/blob/main/examples/llm_finetune/glm/glm_5.3_flash_hellaswag_experts_qat.yaml) | Experimental full pretrained `glm5_next`, expert FP8/FP32 scales, EP32; text-only adaptation |

V4/GLM are **experimental reference configurations**. Earlier successful
full-model QAT smoke tests used synthetic overrides; they do **not** establish
that the published HellaSwag YAMLs ran unchanged. They also do not establish
convergence, task-quality gains or paired QAT-versus-ordinary-training results.
Native serving has not been tested. Scalar/unit tests and tiny/cropped-model GPU
checks are not substitutes for full-model validation of these configurations.

### Run Qwen on one GPU

From the repository root in an already installed CUDA environment:

```bash
CUDA_VISIBLE_DEVICES=0 uv run --no-sync automodel examples/llm_finetune/qwen/qwen3_0p6b_lora_qat.yaml --nproc-per-node 1
```

Qwen needs access to `Qwen/Qwen3-0.6B` and `rajpurkar/squad`. It uses 64 samples,
answer-only supervision, left truncation at 512 tokens, BF16 and HF SDPA.
Keep this recipe at one process; its FSDP2 path skips sharding. `--no-sync` does
not install missing dependencies. For local weights, update both
`model.pretrained_model_name_or_path` and
`dataset.tokenizer.pretrained_model_name_or_path`.

### Full pretrained expert recipes

V4 and GLM use `TrainFinetuneRecipeForNextTokenPrediction`, model-owned
`Config.from_pretrained`, `load_base_model: true` and
`checkpoint.dequantize_base_checkpoint: true`. Preserve the source architecture
and vocabulary; do not replace pretrained loading with full random CPU construction.
MTP is disabled; V4 retains 43 backbone layers, and GLM retains 45 text layers
and its frozen vision branch.

| Model | PEFT / QAT expert target | Notes |
| --- | --- | --- |
| V4 | `model.layers.*.mlp.experts` | 256 experts; 8 local experts at EP32 |
| GLM | `model.language_model.layers.*.mlp.experts` | 288 experts; 9 local experts at EP32; `distributed.moe.wrap_outer_model: true` keeps the frozen vision branch FSDP-owned |

Both recipes use rank-4/alpha-8 LoRA, BF16 base/adapters, zero dropout, QAT from
step zero and activation checkpointing. Keep DoRA, Triton/memory-efficient LoRA,
compilation, TE FP8 and autocast off.

They request 64 HellaSwag training examples, local batch 1/global batch 32 and
two optimizer steps. Padding to a multiple of 64 **does not truncate to 64
tokens**; HellaSwag has no `seq_length` / `max_length` argument. These are not
native chat-format or quality benchmarks. Validation and checkpoint output are
disabled.

### Distributed launch requirements

Targeted training supports one rank or **FSDP2 pure DP sharding** with
`dp_shard_size = world_size`, `dp_replicate_size = 1`, TP=CP=PP=1 and matching
device/MoE meshes. Optional EP must equal world size, divide the expert count,
and use no additional expert-DP sharding/replication. Use `dispatcher: torch`
and `experts: torch` reference loops, including untargeted experts. HSDP, DDP,
Megatron FSDP, autopipeline, HybridEP, DeepEP, `torch_mm`, grouped-MM and MXFP8
expert execution are outside this targeted training gate.

Apply PEFT, then QAT, **before sharding and optimizer construction**. The V4/GLM
examples use four nodes with eight GPUs each: FSDP2 DP-shard32 plus EP32 is
32 ranks, not 1,024. `--nproc-per-node 8` alone does not launch four nodes.
GLM has 288 experts and cannot use EP64. The configured topology does not imply
arbitrary model sizes or sequence lengths fit in memory.

Follow the [Slurm launcher guide](/job-launchers/slurm-cluster) for site-specific
allocation and rendezvous. Set the batch script's `CONFIG` to the V4 or GLM YAML
linked above, allocate **4 nodes × 8 GPUs**, and launch one `torchrun` agent per
node with eight workers and a shared four-node rendezvous. Do not launch these
YAMLs unchanged on one eight-GPU node.

All ranks need model/config/tokenizer and HellaSwag access. For local expert
checkpoints, update these together:
`model.config.pretrained_model_name_or_path`, `model.config.name_or_path` and
`dataset.tokenizer.pretrained_model_name_or_path`, using paths visible on every node.

## Reference export is local-only

The runtime controller is `nemo_automodel._transformers.qat.QAT(config)`:
use `prepare(model)`, `export(model, directory)`, and
`QAT.load_quantized_checkpoint(model, directory)`. `QATConfig.build()` resolves
the configuration; it does not prepare or export a model.

Export requires a **complete, materialized local model in eval mode**. It does
not gather FSDP/EP shards and rejects DTensors or rank-local expert shards, even
after supported distributed training. The examples disable training checkpoint
output; running the CLI does not automatically produce a packed reference export.

Export merges all adapters and packs selected weights into safetensors plus a
manifest. Reload decodes them to floating tensors in an identical non-LoRA
architecture. Retain the architecture and tokenizer: this is not a standalone
Hugging Face `save_pretrained` directory, a training-resume checkpoint, or native
vLLM / TensorRT-LLM packed serving.

### Train, export and reload Qwen locally

To retain the trained Qwen model, run this session from the repository root in
the installed CUDA environment, with exactly one visible GPU and no `torchrun`.
Export before releasing the model; the CLI training command above exits without
retaining it for this session.

```python
from copy import deepcopy

import torch.distributed as dist

from nemo_automodel import NeMoAutoModelForCausalLM
from nemo_automodel._transformers.qat import QAT
from nemo_automodel.components.config.loader import load_yaml_config
from nemo_automodel.recipes.llm.train_ft import TrainFinetuneRecipeForNextTokenPrediction

cfg = load_yaml_config("examples/llm_finetune/qwen/qwen3_0p6b_lora_qat.yaml")
controller = QAT(cfg.qat.qat_config.instantiate())
trainer = TrainFinetuneRecipeForNextTokenPrediction(cfg)
try:
  trainer.setup()  # Applies PEFT and QAT before sharding and the optimizer.
  trainer.run_train_validation_loop()
  model = trainer.model_parts[0]  # Complete, unsharded model on this one rank.
  model.eval()
  controller.export(model, "checkpoints/qwen3_lora_qat_reference")
  fresh = NeMoAutoModelForCausalLM.from_config(
    deepcopy(model.config), dtype="bfloat16", force_hf=True, attn_implementation="sdpa"
  )
  QAT.load_quantized_checkpoint(fresh, "checkpoints/qwen3_lora_qat_reference")
  fresh.eval()
finally:
  if dist.is_initialized():
    dist.destroy_process_group()
```

Use no autocast and enough GPU memory for both models. The controller uses the
same typed config as training. Do not apply this local export session to the
distributed expert recipes.

## What to compare

- **Training effect:** compare ordinary LoRA and QAT from the same pretrained
  base and adapter initialization, with matching data order, steps, optimizer,
  dtype, topology and evaluation inputs. Successful QAT training alone does not
  establish a paired comparison or a quality gain.
- **Same-model reference quantize/decode consistency:** compare each trained
  model's eval output with its own merged, quantized/dequantized reference.
  Include a merge-only control: BF16 merge rounding and operation order can
  change outputs independently of quantization. Low reload error measures
  consistency, not language quality or native low-bit kernel parity.
- **Ordinary expert-LoRA baseline:** a routing-weight placement/reduction bug
  in the ordinary path has been fixed. Older naive comparisons using that
  affected path are invalid evidence of QAT benefit; rerun both arms on the
  corrected implementation rather than attributing the discrepancy to QAT.
- **Deployment quality and efficiency:** evaluate held-out task metrics and
  measure latency, throughput and memory in the actual serving backend.
  Reference decode checks cannot substitute for those measurements.
